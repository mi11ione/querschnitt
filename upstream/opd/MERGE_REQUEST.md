# Merge request: topics for affairs (machine suggestions with provenance, published decisions)

**Proposed for:** OpenParlData data model (`gitlab.com/opendata.ch/openparldatach`), the "Future-Topics/Classification"
item of the OPD wiki. **From:** Querschnitt, Hack Apertus Liebefeld 2026 (Apache-2.0 code, CC BY 4.0 docs).

## 1. What this adds

A topic field for every affair in every parliament, in OPD's own conventions:

| File | |
|---|---|
| `migrations/0001_topics.up.sql` / `.down.sql` | tables `topic_schemes`, `topic_codes`, `topics`; indexes for the API queries; view `topics_current` |
| `migrations/0002_topic_schemes_seed.sql` | the three schemes Querschnitt ships (APS 24 chapters + 190 subtopics + "no policy topic"; ad-hoc "Digitalisierung"; Bern's directorates), generated by `tools/gen_seed.py` |
| `migrations/0003_topic_feed_bodies.up.sql` / `.down.sql` | proposal (§5): per-body switch for the public feed, view `topics_public` |
| `api/topics.md`, `api/models.py` | resource description for `/v1/topics/`, `/v1/affairs/{id}/topics`, `/v1/topic_schemes/` (filters `scheme`, `code`, `body_key`, `lang`, `status`, `since`, …) and Pydantic v2 response models |
| `export/EXPORT.md`, `export/to_opd.py`, `export/sample/` | `topics.ndjson.gz` (or per-body split), `topic_schemes.ndjson.gz`, `topic_codes.ndjson.gz`, index entries |
| `../hop/` | Apache Hop 2.x project: `load_topics.hwf` + `load_topics.hpl` load Querschnitt's `topics.jsonl.gz` into `topics` |

Conventions followed: snake_case; integer `id`; `affair_id` → `affairs.id`, `body_id` → `bodies.id` with `body_key` kept
beside it; language columns `label_de/fr/it/rm` (as `type_harmonized_*`, `name_*`); `created_at` / `updated_at` as UTC
`timestamp`; the `data` + `meta` API envelope; gzipped NDJSON exports with an index entry.

## 2. One row

One row per affair × scheme × level × rank × version. `level` 1 is the APS chapter (or the yes/no of an ad-hoc topic),
level 2 the APS subtopic; `rank` 1 is the label, 2–3 are ranked suggestions. Each row carries its probability (`p`
recalibrated per served build, `p_raw` as the model gave it), a lane (`readings_agree` / `please_check`), one evidence
sentence quoted from the affair with character offsets, and what produced it: served model and build, prompt ids, input
hash, recalibration set, engine version.

## 3. Machine suggestion or decision: always visible

| | `provenance` | `status` | who / when |
|---|---|---|---|
| machine suggestion | `inferred` | `suggested` (enforced by a check constraint) | `model`, `model_build`, `prompt_id`, `input_hash` |
| published confirmation | `confirmed` | `confirmed` | `confirmed_by`, `confirmed_at` (required by a check constraint) |
| published rejection | `confirmed` | `rejected` | same; `confirmed_by_body_id` when the parliament itself publishes it |

A row is never edited except to close it (`valid_to`). A re-score adds a new machine row and closes the old one; a decision
adds a decision row and closes the machine row it decides. History stays queryable (`current=false`, the export).

## 4. Loading and versioning

The Hop workflow (`../hop/README.md`) reads Querschnitt's `topics.jsonl.gz`, keeps machine rows only, compares each row's
content hash with the latest machine row of its key and skips equal rows, looks up `body_id`, `scheme_id` and the labels,
and inserts or updates keyed by `affair_id, scheme_key, level, rank, valid_from` (`topics_version_key`). It then closes
machine rows that a newer machine row supersedes (`valid_to` = the newer `valid_from`). Decision rows are never touched by
the loader, and a machine row closed by a decision does not come back on an identical reload.

Measured on 14 Oct 2026 (Hop 2.19.0, PostgreSQL 16.2, migrations 0001–0003 applied over stub `affairs` / `bodies` tables
filled from the 6 Oct bulk export): first load 15,386 rows; identical reload 15,386 skipped, 0 written; a new export with
one changed row wrote 1 row and closed 1; a published rejection stayed current through the reload.

## 5. Proposal for OPD to decide: who owns a row

Written as a proposal; every point is OPD's call.

1. **Machine suggestions are public, marked, and switched on per body.** The feed and the export carry `inferred` rows as
   machine suggestions. Migration 0003 adds `topic_feed_bodies` (per body and scheme: `inferred_public`,
   `decisions_public`) and the view `topics_public`; without it every body is shown.
2. **A parliament's published rejection replaces the inferred row.** When a parliament service rejects a suggestion and
   chooses to publish that, one transaction adds the decision row and closes the machine row:
   ```sql
   BEGIN;
   INSERT INTO topics (affair_id, body_id, body_key, scheme_id, scheme_key, level, code, parent_code, rank,
                       label_de, label_fr, label_it, label_rm, status, provenance, valid_from,
                       confirmed_by, confirmed_by_body_id, confirmed_at)
   SELECT affair_id, body_id, body_key, scheme_id, scheme_key, level, code, parent_code, rank,
          label_de, label_fr, label_it, label_rm, 'rejected', 'confirmed', now() AT TIME ZONE 'utc',
          'Parlamentsdienste BE', body_id, now() AT TIME ZONE 'utc'
   FROM topics
   WHERE affair_id = :affair_id AND scheme_key = :scheme AND level = :level AND code = :code
     AND provenance = 'inferred' AND valid_to IS NULL;
   UPDATE topics SET valid_to = now() AT TIME ZONE 'utc', updated_at = now() AT TIME ZONE 'utc'
   WHERE affair_id = :affair_id AND scheme_key = :scheme AND level = :level AND code = :code
     AND provenance = 'inferred' AND valid_to IS NULL;
   COMMIT;
   ```
   The default API filter (`status=suggested,confirmed`) then no longer shows the topic for that affair; `status=rejected`
   and the history still do. A confirmation works the same way with `status = 'confirmed'`. If the affair's input changes
   later, the next load adds a new machine row beside the decision; the decision is never overwritten.
3. **Private decisions stay private.** An editor's confirmations, examples and ad-hoc topics in Querschnitt belong to that
   editor (a newsroom, DVS, a parliament service) and reach OPD only when they choose to publish them. OPD's table holds
   published rows only.
4. **Open for OPD:** how a parliament publishes a decision (an authenticated endpoint, a file in the Hop folder, or the
   parliament's own export picked up by OPD's existing adapters); whether `confirmed_by` names a person or only the service.

## 6. Questions for OPD and APS

- APS: may OPD publish APS subtopic labels and level-2 rows? Until agreed, the export and the public feed carry chapters
  (level 1) and ad-hoc topics only; the table can hold level 2 already.
- Single `topics.ndjson.gz` or per-body split (`export/EXPORT.md`).
- Whether `topic_feed_bodies` (0003) is wanted, or every body is shown from the start.
- The licence statement for the exported table (Querschnitt's rows are CDLA-Permissive-2.0).
- Migration tooling: the files are plain SQL in transactions; they can be wrapped in whatever OPD uses.
