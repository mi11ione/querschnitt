# Merge request: topic tables for affairs (machine suggestions and published decisions, kept apart)

Draft for the hackathon (shown to OPD at the event, not filed). Target: the OpenParlData data model and ETL (`gitlab.com/opendata.ch/openparldatach`), the
"Future-Topics/Classification" item of the OPD wiki. From: Querschnitt, Hack Apertus Liebefeld 2026. Code Apache-2.0,
documentation CC BY 4.0, topic rows CDLA-Permissive-2.0.

## Summary

OPD has no topic field on affairs. This MR adds one, as three tables in OPD's conventions, a loader in Apache Hop, an API
resource description with its read endpoints as a FastAPI router, and a bulk-export spec. Every row says whether a model suggested it (`provenance = 'inferred'`) or a
person or parliament decided it (`provenance = 'confirmed'`), and which model build, prompt and input produced it. The
rows come from Querschnitt, which reads OPD's published bulk exports and classifies each affair with Apertus
(`swiss-ai/apertus-v1.5-8b`) as a closed choice from a code list. Nothing in this MR calls a model; OPD loads a file.

## Data model

Conventions taken from OPD's tables and exports: snake_case; integer `id`; `affair_id` → `affairs.id` and `body_id` →
`bodies.id` with `body_key` kept beside it; language columns `label_de/_fr/_it/_rm`; `created_at` / `updated_at` as
`timestamp` holding UTC; `position` and `external_id` as on other tables.

One `topics` row per affair × scheme × level × rank × version. Level 1 is the APS chapter (or the yes/no of an ad-hoc topic,
or a parliament's own code), level 2 the APS subtopic; rank 1 is the label, ranks 2–3 are ranked suggestions. A row
carries `p` (recalibrated, rank 1 only) and `p_raw`, a `lane`, one evidence sentence quoted from the affair with
character offsets, and what produced it: `model`, `model_build`, `prompt_id`, `input_hash`, `cutoffs_id`,
`engine_version`.

| | `provenance` | `status` | who / when |
|---|---|---|---|
| machine suggestion | `inferred` | `suggested` (check constraint) | `model`, `model_build`, `prompt_id`, `input_hash` |
| published confirmation | `confirmed` | `confirmed` | `confirmed_by`, `confirmed_at` (check constraint) |
| published rejection | `confirmed` | `rejected` | same; `confirmed_by_body_id` when the parliament itself publishes it |

A row is never edited except to close it (`valid_to`). A re-score adds a machine row and closes the old one; a decision
adds a decision row and closes the machine row it decides. History stays queryable (`current=false`, the export).

`lane` takes three values (check constraint): `please_check` means a person should look; `pass` and `readings_agree` both
mean no check was asked for. `pass` is the APS chapter rule since 14 Oct (recalibrated `p` at least 0.7 and, in bilingual
parliaments, German and French readings agree); ad-hoc topics, parliament schemes and APS rows from before that date
carry `readings_agree`. The exact rules per scheme are in `opd/api/topics.md`, "Row".

## How good the rows are

Measured, with sources in Querschnitt's `eval/` (every figure is a row in `eval/claims.tsv`):

- APS chapter on 927 federal affairs labelled by the APS editors and not looked at while building: right in 0.696
  [0.666, 0.726] (646/927).
- Lane on the same affairs: 67.3% pass without a check and are right in 0.812 [0.779, 0.842]; the 32.6% marked
  `please_check` are right in 0.458 [0.403, 0.516].
- APS subtopics are suggestions: 0.520 top-1, never a lane of their own.
- Communal affairs of 2026 have no human labels; against a blind AI judge the chapter agrees in 0.640 [0.571, 0.704].
- A parliament's own scheme without descriptions (Basel-Stadt, 2,437 hand-tagged motions): 0.498 [0.478, 0.518].
- Ad-hoc "Digitalisierung": 27/30 of the public DVS list recognised; that list is not held out. Narrow ad-hoc topics
  over-flag (precision of flags 0.225 / 0.670 / 0.136 for wolves / heat / AI in schools against the judge); a second
  question on each flag sends unconfirmed ones to `please_check`.
- Cost at Public AI list price: USD 0.333 per 1,000 affairs for chapter, subtopic and one ad-hoc topic.

## Loading and versioning

The Hop workflow reads `topics.jsonl.gz`, keeps machine rows only, compares each row's content hash with the latest
machine row of its key and skips equal rows, maps the evidence source to `evidence_text_id` / `evidence_doc_id` as the
converter does, looks up `body_id`, `scheme_id` and the labels, and inserts by `(affair_id, scheme_key, level, rank,
valid_from)` with `updated_at` = the load time. It then closes machine rows that a newer machine row supersedes.
Decision rows are never touched by the loader; a machine row closed by a decision does not come back on a reload.

## Changing a scheme, adding an ad-hoc topic

`0002` is the initial seed. A changed scheme file, or an ad-hoc topic created later in Querschnitt (each is one file in
`src/querschnitt/schemes/`), needs its `topic_schemes` row before the next load, or the load stops on the NOT NULL
`scheme_id`. `python3 opd/tools/gen_seed.py --scheme adhoc/<slug> --name 0004_topic_scheme_<slug>` writes that
migration: it deactivates the scheme's current version, adds the new version (identity id) with its codes, and its down
migration reverses that. Rows already loaded keep the version and labels they were loaded with.

## When the served model build changes

Every row names its build (`model_build`). Querschnitt's batch stops when the served build changes in the middle of a run,
so one run never mixes builds. The recalibration (`p`) and the lane cut-off are fitted per build on human-labelled items;
the procedure for a new build is: probe the endpoint, replay stored items, and refit before any number from the new
build is published (Querschnitt `docs/ONSITE.md`, gate thresholds there). Two things follow for OPD:

- Querschnitt re-scores only new and changed affairs, so the table holds rows of several builds side by side; a build
  change does not re-version the whole table.
- The refit is a manual step. Until it is done, Querschnitt applies a calibration only to rows of the build it was
  fitted on: rows of another build carry `p` null, no `cutoffs_id`, and the APS chapter lane from the readings alone,
  and composing them logs one warning per build (Querschnitt `docs/CONTRACT.md` §1). A file with a new build therefore
  loads without a recalibrated `p` on that build's rows until the refit; `SELECT DISTINCT model_build, cutoffs_id` on
  the table shows which builds are calibrated.

## Who owns a row (proposal; every point is OPD's call)

1. **Machine suggestions are public, marked, and switched on per body.** The feed and the export carry `inferred` rows as
   machine suggestions. Migration 0003 adds `topic_feed_bodies` (per body and scheme: `inferred_public`,
   `decisions_public`) and the view `topics_public`; without it every body is shown.
2. **A parliament's published rejection replaces the inferred row.** One transaction adds the decision row and closes the
   machine row:
   ```sql
   BEGIN;
   INSERT INTO topics (affair_id, body_id, body_key, scheme_id, scheme_key, level, code, parent_code, rank,
                       label_de, label_fr, label_it, label_rm, status, provenance, valid_from,
                       confirmed_by, confirmed_by_body_id, confirmed_at)
   SELECT affair_id, body_id, body_key, scheme_id, scheme_key, level, code, parent_code, rank,
          label_de, label_fr, label_it, label_rm, 'rejected', 'confirmed', now() AT TIME ZONE 'utc',
          'Parlamentsdienste BE', body_id, now() AT TIME ZONE 'utc'
   FROM topics
   WHERE affair_id = :affair_id AND scheme_key = :scheme AND level = :level AND code = :code
     AND provenance = 'inferred' AND valid_to IS NULL;
   UPDATE topics SET valid_to = now() AT TIME ZONE 'utc', updated_at = now() AT TIME ZONE 'utc'
   WHERE affair_id = :affair_id AND scheme_key = :scheme AND level = :level AND code = :code
     AND provenance = 'inferred' AND valid_to IS NULL;
   COMMIT;
   ```
   The default API filter (`status=suggested,confirmed`) then no longer shows the topic for that affair; `status=rejected`
   and the history still do. A confirmation works the same way with `status = 'confirmed'`. If the affair's input changes
   later, the next load adds a new machine row beside the decision; the decision is never overwritten.
3. **Private decisions stay private.** Confirmations made in Querschnitt by an editor (a newsroom, DVS, a parliament
   service) reach OPD only when that editor publishes them. OPD's table holds published rows only.
4. **Open:** how a parliament publishes a decision (an authenticated endpoint, a file in the Hop folder, or the
   parliament's own export picked up by OPD's adapters); whether `confirmed_by` names a person or only the service.

## Licensing

- Topic rows: CDLA-Permissive-2.0 from Querschnitt; which licence the OPD export states for the table is OPD's decision.
  `evidence_quote` is a verbatim substring of the affair's text as OPD publishes it.
- Labels follow their scheme (`topic_schemes.licence`): ad-hoc questions written by Querschnitt CC-BY-4.0; Basel-Stadt's
  themes CC-BY-4.0 (OGD dataset 100086); APS and Bern's directorate names NULL, to be agreed with the source.
- APS subtopic labels and level-2 rows: not public until APS agrees. The table holds them; the export, the API rule in
  `opd/api/topics.md` and the `topics_public` view leave them out.

## Who runs the nightly, and what a night costs

- **Today: the author's laptop.** `ops/nightly.sh` (macOS, started daily at 09:15 by `ops/nightly-loop.sh`, after OPD's
  morning export) fetches the new export, scores new and changed affairs with Apertus and writes the store. The topics
  file OPD would load is published by hand as a release asset (`tools/make_data_release.sh` builds it; publishing is a
  separate step). Not a service OPD can rely on.
- **For OPD: the same job as a container, already in the repo.** `docker-compose.yml` profile `lite` (service
  `nightly-lite`: chapters and subtopics, sized for OPD's VPS) or profile `full` (service `nightly`, with its own
  Postgres, API and app). Both run `querschnitt nightly`: `delta --since yesterday` once a day at `QS_NIGHTLY_AT`
  (default 02:30); a failed night is logged and the next night retries. Lite keeps Querschnitt's working store in the
  Postgres named by `QS_PG_DSN`, which may be OPD's own: its tables are all `qs_*` (`qs_topics`, `qs_affairs`, ...) and
  it never touches this MR's `topics`. The hand-off into `topics` is the Hop load: every lite night ends by writing the
  topics file (the store's current machine rows, the format of `hop/README.md`) to `/app/out/topics.jsonl.gz` in volume
  `topics_out`, and step 6 of "Day 1" loads it. CI runs that path (job `hop`, after the release load): Querschnitt's
  store in the same database as the migrated tables, `topics` unchanged by it, its file loaded by Hop and checked row
  by row against `opd/export/to_opd.py`. Without containers, a
  scheduled job (cron or a CI schedule) can run `querschnitt delta --since yesterday` once a day. The endpoint and its key
  come from the environment (`QS_BASE_URL`, `QS_MODEL`, `QS_API_KEY`); whoever holds the key pays for the calls. Open: who
  at OPD owns the job and the key.
- **Cost of a night, measured on 15 Oct** (`eval/nightly/2026-10-15.json`): OPD's export of that day had 33 new affairs;
  49 affairs were scored for USD 0.0215 at list price, in 9.6 minutes once the endpoint answered with the locked build,
  and 0 rows were left in the queue.
- **That night was not unattended.** The 09:15 scheduled run skipped the fetch (a bug in `ops/nightly.sh`, fixed the
  same morning). The cut pass at 09:31 and the drain at 14:52 were both started by hand: the endpoint was back at 11:05,
  but the Mac had restarted and the recovery was missed (`eval/nightly/2026-10-15.log`). No row was lost.
- **Automatic resume after an outage** exists since 15 Oct: a run stopped by endpoint errors resumes by itself once the
  endpoint answers with the build the run locked (`ops/endpoint_ok.py`, called by `ops/watchdog.sh` and `ops/pipeline.py`;
  three resumes without a successful call leave the run stopped for a person). The nightly itself has not yet run a full
  outage night unattended.

## Rollback

- Stop: disable the Hop job. The rows stay; nothing else writes to the tables.
- Remove: export the tables first (`opd/export/to_opd.py` or OPD's own dump), then roll back in reverse order:
  `0003 down` (drops the feed switch and `topics_public`), `0002 down` (deletes the seeded scheme versions, their codes
  and the topic rows loaded against them), `0001 down` (drops the tables and `topics_current`). `0001 down` fails while
  0003 is applied, and `0002 down` fails while `topic_feed_bodies` references a scheme; both by foreign key or
  dependency, so nothing is dropped half-way.
- A later `--scheme` migration rolls back on its own: its down removes that version and reactivates the previous one.

## Known gaps before a merge

  of those affairs go with them. OPD to confirm how affairs are updated; otherwise drop the cascade.
